## 二、逐项目核心代码原理与工程特点深度剖析

### 1. `prompt-optimizer` ([affaan-m/everything-claude-code](https://explainx.ai/skills/affaan-m/everything-claude-code/prompt-optimizer))

* **本地源码路径**：[`01-community-skills/affaan-m-everything-claude-code/prompt-optimizer/SKILL.md`](../01-community-skills/affaan-m-everything-claude-code/prompt-optimizer/SKILL.md)
* **核心架构原理（6 阶段确定性诊断与编排流水线）**：
  1. **严格的角色隔离（Advisory-Only Guardrail）**：在源码头部通过强指令锁定边界——`Advisory role only — never executes the task itself. Do NOT write code, create files, run commands...`，并在 `Do Not Use When` 中显式排除“优化代码 (`optimize this code`)”、“优化性能 (`optimize performance`)”与“直接做 (`just do it`)”，彻底杜绝 Agent 将“优化提示词”误判为“直接写代码”。
  2. **Phase 0 环境上下文自动探测（Project Detection）**：打破传统提示词生成器“盲猜背景”的缺陷，要求 Agent 先读取工作目录中的 `CLAUDE.md` 与构建配置（`package.json`、`pyproject.toml`、`go.mod`、`Cargo.toml`、`pom.xml` 等），自动识别语言框架与工程约定，并注入后续阶段。
  3. **Phase 1–3 多维矩阵映射（Intent × Scope × Tech Stack）**：
     * **意图分类（9 类）**：通过中英文信号词矩阵识别 `New Feature`、`Bug Fix`、`Refactor`、`Research`、`Testing`、`Review`、`Documentation`、`Infrastructure`、`Design`。
     * **规模分级（5 级）**：按修改范围划分为 `TRIVIAL`（单文件 <50 行）、`LOW`（单组件）、`MEDIUM`（多组件同域）、`HIGH`（跨模块 5+ 文件）、`EPIC`（跨会话架构级迁移）。
     * **生态组件绑定**：自动将任务映射到标准化命令链（如 `/plan` → `/tdd` → `/code-review` → `/verify`）及专项子代理（如 `planner`、`tdd-guide`、`security-reviewer`）。
  4. **Phase 4 缺失上下文 11 项扫描与追问门控（Missing Context Gate）**：逐项核查技术栈、目标文件范围、验收标准、错误处理、安全要求、测试预期、性能约束、UI/UX、数据库变更、现有模式参考及**禁止范围（Scope boundaries — What NOT to do）**。当缺失项 ≥ 3 项时，触发最多 3 个澄清问题。
  5. **Phase 5 模型分级路由与多会话拆分**：针对 `HIGH`/`EPIC` 任务推荐“Opus 负责 `/plan` 或 `blueprint` 架构规划 + Sonnet 负责分阶段执行”，并利用 `/save-session` 与 `/resume-session` 将大任务拆分为多条序列化 Prompt。
* **核心工程特点**：
  * **研发工作流强绑定**：生成的 Prompt 并非孤立文本，而是包含“规划 → 测试先行（TDD）→ 编码 → 代码审查 → 验证”闭环的可执行工程规范。
  * **双版本输出（Full + Quick）**：同时输出面向完整上下文的 `Full Version` 和面向熟练开发者的单行命令链 `Quick Version`，兼顾详尽度与复用效率。

### 2. `prompt-master` ([nidhinjs/prompt-master](https://github.com/nidhinjs/prompt-master/blob/main/SKILL.md))

* **本地源码路径**：
  * 主技能定义：[`01-community-skills/nidhinjs-prompt-master/SKILL.md`](../01-community-skills/nidhinjs-prompt-master/SKILL.md)
  * 37 种反模式库：[`01-community-skills/nidhinjs-prompt-master/references/patterns.md`](../01-community-skills/nidhinjs-prompt-master/references/patterns.md)
  * 13 套场景模板库：[`01-community-skills/nidhinjs-prompt-master/references/templates.md`](../01-community-skills/nidhinjs-prompt-master/references/templates.md)
* **核心架构原理（基于上下文注意力曲线的 30/55/15 分区架构）**：
  1. **PAC 30/55/15 位置注意力架构（Positional Attention Architecture）**：
     * 针对大模型在长上下文中的 U 型注意力衰减规律（[Lost in the Middle, Liu et al., TACL](https://levelup.gitconnected.com/prompt-master-claude-skill-any-ai-264e4949d2f3)），`SKILL.md` 将自身指令及生成的目标 Prompt 严格划分为三个区域：
       * **PRIMACY ZONE（前 30% 首因区）**：放置身份定义、不可违背的硬性约束（Hard Rules）、记忆继承块（`Memory Block`）以及输出格式锁（Output Lock），确保核心边界不受注意力衰减影响。
       * **MIDDLE ZONE（中间 55% 执行与路由区）**：放置 9 维意图提取表、30+ 模型/工具路由表与故障诊断清单等按需检索的字典型内容。
       * **RECENCY ZONE（后 15% 近因区）**：放置交付前的 6 项强制自检清单（Verification and Success Lock）与强信号词核验。
  2. **跨模型家族与工具的精细化差异路由（Differential Tool Routing）**：
     * **推理模型（`o3`、`o4-mini`、`DeepSeek-R1`、`Qwen3-thinking`）**：明确規定 **严禁添加 CoT（`"think step by step"`）或推理脚手架**，因为推理模型已在内部消耗数千推理 Token，外部 CoT 反而会劣化输出并浪费 Token；要求系统提示词控制在 200 词以内，仅声明目标与完成标准。
     * **指令与多模态模型（Claude、GPT、Gemini、Midjourney、ComfyUI）**：为 Claude 启用 XML 结构化标签与自适应思考（Adaptive Thinking）；为 Gemini 强制注入防引用幻觉锚点（`"Cite only sources you are certain of. If uncertain, say [uncertain]."`）；为 Midjourney 切换为逗号分隔视觉描述符与尾部参数（`--ar 16:9 --v 6 --style raw`）；为 ComfyUI 拆分为独立的 `POSITIVE PROMPT` 与 `NEGATIVE PROMPT` 节点块。
     * **自主编码 Agent（Claude Code、Cursor、Devin）**：强制要求包含 `Starting State`、`Target State`、`Allowed/Forbidden Actions`、`Stop Conditions`（停止条件与人类审批门控）以及 `✅` 步骤检查点。
  3. **高幻觉伪技术黑名单（Anti-Fabrication Filter）**：
     * 源码在 `Hard rules` 中显式封禁了在单次前向推理（Single-Prompt）中容易诱发角色扮演幻觉的复杂框架：模拟多专家路由（Simulated MoE）、无外部搜索引擎的思维树/思维图（ToT / GoT）、无独立采样通道的自洽性（USC），以及索要隐藏思维链（Hidden CoT），全面替换为可审计推理契约（**Template E — Auditable Reasoning**：仅要求输出结论、假设、证据、核验项与剩余不确定性）。
  4. **按需加载的参考库设计（Progressive Context Disclosure）**：
     * 将 13 套结构化模板（`RTF`、`CO-STAR`、`RISEN`、`CRISPE`、`Auditable Reasoning`、`Few-Shot`、`File-Scope`、`ReAct + Stop Conditions` 等）与 37 种浪费 Token 的坏模式（`Credit-Killing Patterns`）剥离到 `references/` 子目录，指示模型仅在命中对应任务类别时按需读取，极大降低了日常调用的上下文开销。

### 3. `anthropic-prompt-engineer` ([zircote/.claude](https://github.com/zircote/.claude/blob/main/skills/anthropic-prompt-engineer/SKILL.md))

* **本地源码路径**：[`01-community-skills/zircote-claude/anthropic-prompt-engineer/SKILL.md`](../01-community-skills/zircote-claude/anthropic-prompt-engineer/SKILL.md)
* **核心架构原理（Anthropic 官方六大工程支柱与模块化参考体系）**：
  1. **六大核心技术原语封装**：
     * **Be Clear and Direct**：消除隐式假设，提供无歧义的显式指令。
     * **Use XML Tags for Structure**：利用 Claude 原生训练偏好，通过 `<instructions>`、`<context>`、`<example>` 等语义化 XML 标签实现指令与数据的物理隔离。
     * **Chain of Thought (CoT)**：针对复杂逻辑任务引导分步推演。
     * **Prefilling（助手回复预填充）**：通过预先给定 Assistant 回复的开头字符（如 `{` 或 `<answer>`）锁定输出格式与语气。
     * **Few-Shot Examples**：提供 2–5 个覆盖边界情况的多样化输入/输出对（Show, don't just tell）。
     * **Role Assignment**：通过领域专家身份设定收紧词汇分布与分析视角。
  2. **主文件轻量化 + 5 大专题 Reference 索引架构**：
     * `SKILL.md` 仅保留 136 行高密度导航与 8 项最佳实践核对清单（`Best Practices Checklist`），将具体模板与进阶技巧解耦至 `references/` 目录（`core_techniques.md`、`advanced_techniques.md`、`common_mistakes.md`、`claude_4_best_practices.md`、`prompt_templates.md`），体现了“Context as Resource（每个 Token 都是资源）”的设计哲学。

### 4. `github/awesome-copilot` (`prompt-optimizer` [SKILL.md](https://github.com/github/awesome-copilot/blob/main/skills/prompt-optimizer/SKILL.md))

* **本地源码路径**：[`01-community-skills/github-awesome-copilot/prompt-optimizer/SKILL.md`](../01-community-skills/github-awesome-copilot/prompt-optimizer/SKILL.md)
* **核心架构原理（“零占位符”双态状态机与認知心理学重写工作流）**：
  1. **最高优先级双铁律（Two Hard Rules）**：
     * **Rule 1 — No placeholders. Ever.**：严厉禁止在生成的提示词中出现 `[paste X here]`、`[your content]`、`{topic}`、`<your_input_here>` 等任何需要用户二次手动填空的中括号或模板变量。源码甚至写入了强自检指令：`If you catch yourself typing square brackets around a noun, stop. That's a placeholder. Rewrite.`
     * **Rule 2 — Case A / Case B 双态闭环处理**：
       * **Case A（用户已提供真实数据/草稿/代码）**：将用户提供的原始数据直接烘焙（Bake in）进优化后的完整提示词代码块中，用户复制粘贴即可一键发送。
       * **Case B（用户仅描述了一类通用任务，未给具体输入）**：将提示词编写为**自带交互引导逻辑的完备指令**——要么在提示词末尾命令目标大模型先向用户反问所需信息（`"Before drafting, ask me to share the product name, audience, and a link."`），要么声明下一步将粘贴数据（`"I'm about to share a batch of emails with you in my next message..."`）。
  2. **高杠杆认知优化法则（Core Principles）**：
     * **长输入置顶原则（Put long inputs on top, the question on the bottom）**：源码明确指出，当包含长文档、转录稿或数据转储时，将其放在提示词顶部、指令放在底部，在长上下文任务中可带来最高约 **30% 的质量提升**。
     * **先引述后作答（Quote-First Grounding）**：针对长文档分析，强制要求模型先将原文依据提取至 `<quotes>` 标签内，再基于引文作答，从根源上抑制长文漂移与幻觉。
     * **解释原因（Explain the why）**：不仅告诉模型“做什么”，还用一句话说明背后的工程原因（如 `"Avoid ellipses, because the output will be read aloud by a TTS engine that mispronounces them"`），利用模型的泛化推理能力提升指令遵循度。
     * **正向祈使与范围字面化（Positive Framing & Literal Scope）**：用正向句式替代否定句式；明确声明 `"apply this to every section, not just the first one"`；在代码审查场景下强调“发现阶段的目标是全覆盖而非过滤（coverage, not filtering）”，要求同时输出 `Confidence` 与 `Severity` 供下游筛选。
     * **末尾深度推理触发行（Closing-Line Reasoning Trigger）**：不在提示词中间堆砌杂乱的思考指令，而是在全文末尾统一追加一句推理深度信号（如 `"Think before answering (maximum reasoning)"` 或 `"Take time to think through this carefully before responding."`）。

### 5. 官方内置生成工具：[Anthropic Console Metaprompt](https://platform.claude.com/cookbook/misc-metaprompt) & [OpenAI Meta-Prompt](https://developers.openai.com/api/docs/guides/prompt-generation)

* **本地源码路径**：
  * Anthropic 官方源码：[`02-official-and-frameworks/anthropic-metaprompt/anthropic_metaprompt.py`](../02-official-and-frameworks/anthropic-metaprompt/anthropic_metaprompt.py)
  * OpenAI 官方源码与评测闭环：[`02-official-and-frameworks/openai-meta-prompt/openai_meta_prompt.py`](../02-official-and-frameworks/openai-meta-prompt/openai_meta_prompt.py)
* **Anthropic Metaprompt 核心原理**：
  1. **高复杂度 Few-Shot 元示范（5 个完整 `<Task Instruction Example>`）**：通过 5 个覆盖不同认知范式的长示例（客服 FAQ 严格边界 + `<thinking>` 原文摘录、句子同义判定、文档问答 `<Relevant Quotes>` 编号引用、苏格拉底数学导师 `<Inner monologue>` 逐步逆向验算、工具调用 `<scratchpad>` 异常捕获与重试），直接向模型展示“什么是工业级好 Prompt”。
  2. **三步式结构化编译（`<Inputs>` → `<Instructions Structure>` → `<Instructions>`）**：
     * 第一步先提取最小无重叠的输入变量集合（`{$VAR}` 格式）；
     * 第二步在 `<Instructions Structure>` 中规划变量位置（强制要求长文本输入变量出现在处理指令之前）；
     * 第三步生成最终 `<Instructions>`，并内置“理由必须在评分之前（Justification before score）”与复杂任务 `<scratchpad>` 思考区规则。
  3. **后 Prefill 时代的响应引导（Response Steering）**：针对 Claude 4.6+ 移除 API 端 Assistant Prefill 的变化，源码通过在 User Prompt 尾部追加强引导指令（`"Start your response directly with the <Inputs> block. Do not include any preamble..."`）实现零废话结构化提取。
* **OpenAI Meta-Prompt 核心原理**：
  1. **“先推理后结论”铁律（Reasoning Before Conclusions）**：源码中以全大写强信号词声明：`ATTENTION! If the user provides examples where the reasoning happens afterward, REVERSE the order! NEVER START EXAMPLES WITH CONCLUSIONS!`。因为自回归模型按 Token 从左到右生成，若先输出结论或分类标签，后续的“理由”就会退化为对既定结论的事后合理化（Post-hoc Rationalization）。
  2. **常量防注入与用户资产保留（Constants & Preservation）**：明确指示保留用户提供的评分量表（Rubrics）、指南与示例作为系统常量（Constants），抵抗用户输入端 Prompt Injection。
  3. **标准化五段式 System Prompt 骨架**：强制输出为 `[首行无标题核心指令]` → `# Steps` → `# Output Format` → `# Examples`（支持占位符与真实长度说明）→ `# Notes`。
  4. **Meta-Prompt + LLM-as-a-Judge 量化迭代闭环**：在 [OpenAI Meta-Prompting Cookbook](https://developers.openai.com/cookbook/examples/enhance_your_prompts_with_meta_prompting) 中，官方展示了用高阶推理模型生成增强版 Prompt，在测试集上并发运行后，通过 Pydantic `ScoreCard`（将 `justification: str` 置于各项 1–5 分整数指标之前）调用 `client.beta.chat.completions.parse` 进行自动化裁判打分，从而实现基于数据的提示词迭代。

### 6. 编程式提示词优化框架：[DSPy (`stanfordnlp/dspy`)](https://github.com/stanfordnlp/dspy/blob/main/dspy/teleprompt/mipro_optimizer_v2.py)

* **本地源码路径**：
  * `MIPROv2` 编译器源码：[`02-official-and-frameworks/dspy/mipro_optimizer_v2.py`](../02-official-and-frameworks/dspy/mipro_optimizer_v2.py)
  * `Signature` 声明式契约源码：[`02-official-and-frameworks/dspy/signature.py`](../02-official-and-frameworks/dspy/signature.py)
* **核心架构原理（将自然语言 Prompt 转化为可微/可搜索的参数空间）**：
  1. **契约与实现分离（`Signature` 元类机制）**：
     * 在 [`signature.py`](../02-official-and-frameworks/dspy/signature.py) 中，`SignatureMeta` 继承自 Pydantic `BaseModel` 元类，将提示词拆解为两部分：
       * **静态类型契约**：通过 `InputField` 和 `OutputField` 定义输入输出字段名、类型注解（AST 解析支持复杂泛型）及字段前缀/描述（`json_schema_extra["prefix"]` / `["desc"]`）。
       * **可变异指令超参数**：将类文档字符串 `cls.__doc__` 映射为 `cls.instructions` 属性，并提供不可变变换方法 `Signature.with_instructions()`、`with_updated_fields()` 以及状态序列化方法 `dump_state()` / `load_state()`。
  2. **`MIPROv2` 三阶段自动化提示词编译（Compile Pipeline）**：
     * **Stage 1 — 基于评估指标的自举 Few-Shot 采样（`_bootstrap_fewshot_examples`）**：调用 `create_n_fewshot_demo_sets`，让 Teacher/Student 模型在训练集上运行并收集完整轨迹（Traces），仅保留通过用户定义的 `self.metric` 校验的高分轨迹，组装成 $N$ 组候选 Few-Shot 示例集。
     * **Stage 2 — 四维感知指令提案（`_propose_instructions` & `GroundedProposer`）**：不同于盲目改写词语，`GroundedProposer` 同时注入 4 类上下文来生成每个模块的 $N$ 条候选自然语言指令：
       1. `program_aware`：扫描整个 DSPy 程序的控制流代码，理解当前模块在全局流水线中的角色；
       2. `data_aware`（`use_dataset_summary`）：对训练集做批量采样摘要，捕捉真实数据分布特征；
       3. `fewshot_aware`（`use_task_demos`）：参考 Stage 1 自举出的成功输入/输出示范；
       4. `tip_aware`（`use_tip`）：随机注入多样化提示词工程启发式技巧（如“鼓励分步推理”、“强调边界条件”），拓宽候选指令的探索空间。
     * **Stage 3 — 多变量贝叶斯离散搜索（`_optimize_prompt_parameters`）**：
       * 将流水线中每个 Predictor 的“候选指令索引（`i_predictor_instruction`）”与“候选 Few-Shot 集合索引（`i_predictor_demos`）”建模为分类超参数分布（`CategoricalDistribution`）。
       * 引入 Optuna 的多变量树结构 Parzen 估计器（`TPESampler(multivariate=True)`），在验证集的小批量样本（`minibatch_size=35`）上进行快速评估更新代理模型，并每隔 `minibatch_full_eval_steps` 轮对平均得分最高的候选组合执行一次全量验证集评估（`_perform_full_evaluation`），最终返回全局得分最高并可持久化为 JSON 的最优提示词组合。
  3. **自反思演化扩展（`SIMBA` & `GEPA`）**：
     * 如 [DSPy Optimizers 官方文档](https://github.com/stanfordnlp/dspy/blob/main/docs/docs/learn/optimization/optimizers.md) 所示，DSPy 进一步提供了基于轨迹反思的优化器（如 `SIMBA` 识别高方差困难样本并自省生成改进规则，`GEPA` 利用大模型对失败轨迹和领域文本反馈做反思式提示词演化），这正是将静态 Skill 升级为“自演进 Agent”的核心算法原型。
